What this lab is for

Write tests from unit level (one rail on one board) up to system level (a board, its instruments, and an operator) in one place, run them interactively, and keep the results as verification evidence. The lab tries three ideas:

  1. Targets with interfaces, commands, and telemetry, as COSMOS has them, defined in plain text, so a test says PSU.set_voltage 24 V and check MAIN.rail_3v3 3.3 V ±3% and never deals with SCPI strings or serial framing.
  2. One step per line, so the text and the rows are the same thing (as Scribe's document and diagram are). Simple tests never need code; the script step, in Python, is the escape hatch for loops and searches.
  3. Needs come from the steps. A test that uses SCOPE needs the scope; detach it and that test skips with a reason. That's how one suite scales from a board on a desk to a full bench, with no tiers to keep up by hand.

How it would talk to hardware

  • Direct from the page: Web Serial for COM ports, and WebUSB for USB devices, as Flasher already does. USBTMC instruments work over WebUSB, but on Windows only once the instrument uses the WinUSB driver (Zadig), which takes it away from NI-VISA.
  • Through a local bridge: browsers can't open raw TCP sockets, so LAN instruments (SCPI on port 5025), VISA, and sigrok logic analyzers need a small Python agent on the bench PC (PyVISA, pyserial, sigrok) that the page reaches over a localhost WebSocket. The same agent could run tests headless.
  • Plotting cost: each point keeps 10 minutes at up to 20 Hz in a ring buffer (about 140 KB), and the plot draws one column per pixel, so ten points over 10 minutes (120,000 samples) draw in about 10 ms. The real limit is the instruments: the tool should poll only what's plotted, on screen, or used by a running test, at a rate each interface can answer.
  • Headless: a Python runner reads the same test text and target definitions, so CI and Claude can run a suite and the page shows the results.

Where it fits the suite

  • A test lists the requirements it verifies ([REQ-004]). A run becomes evidence on those requirements in Signoff EE or FW, and Signoff PL rolls it up.
  • Flasher puts firmware on the board; a suite's first step could be "flash this release". Bring-up checklists in Signoff EE could link to the test that covers them.
  • Targets and suites would live in a private data repo like the other tools; results as one file per run.

Decided (2026-11-23)

  • Name: Plumb, checking that something is true, after the suite's shop words (Dovetail, Jig).
  • Python everywhere. The script step is Python, run in the browser by Pyodide (CPython compiled to WebAssembly) in a Worker; the first script loads about 10 MB once, then Python stays loaded. The local bridge and the headless runner are Python too (PyVISA, pyserial, and sigrok's bindings), so a test's script runs the same in the page and on the bench PC.

Decisions to make

  1. Where Pyodide comes from. This lab loads it from the jsDelivr CDN inside the Worker. The suite's pages load nothing from outside, so the real tool would either host Pyodide's files itself (about 10 MB in the repo or a release) or allow that one CDN.
  2. The bridge's job: only a pipe to instruments the page can't reach, or also the place a long or unattended run happens.
  3. A failed check: in this lab a failed check marks the test failed and carries on, while a wait until timeout or an error stops it. pytest stops at the first failure.
  4. Call and cleanup: here a called test's cleanup waits until the calling test ends, so call PWR-01 powers up and the supply goes off only at the very end.
